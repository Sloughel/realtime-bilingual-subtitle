# 扩展点与二次开发指南

> 面向 01 文档 §2.3 的**二次开发者**角色：拿到仓库后想在 30 分钟内接上自己的模型、
> 加一门语言、换一种音频源，或把服务端部署到自己的服务器上。
>
> 本文件只讲"改哪里、怎么验证"，不复述需求与设计理由——那些见 01/02/03 文档。
> M4 扩展（E1/E2/E3）的实际落地记录见 [`10-M4扩展实施记录.md`](10-M4扩展实施记录.md)。

## 1. 三层可替换点一览

整个系统有 4 个稳定的扩展面，全部是**接口/配置级**改动，不需要动协议：

| 扩展面 | 位置 | 替换方式 | 典型需求 |
|---|---|---|---|
| 翻译后端 | `server/app/translate.py` 的 `Translator` Protocol | 新增一个类，实现 `async translate()` | 换厂商、换本地模型（E2 已实现 Ollama） |
| 语音识别 | `server/app/asr.py` 的 `ASREngine` | 保持 `transcribe_async(pcm, language) -> str` | 换 whisper 规格、换 ASR 引擎 |
| 音频源（客户端） | `android/.../audio/AudioSource.kt` | 实现 `start(onFrame)` / `stop()` | 新增采集方式（如蓝牙、文件回放） |
| 语言对 | `server/app/protocol.py` 的 `LANG_NAMES` / `SUPPORTED_LANGS` | 加枚举取值 | 中→英、日→中（S1） |

> **边界**：以上任何一项都**不新增消息类型**（01 文档 §3 边界声明）。新增能力只能通过
> 扩充枚举取值、配置项，或在服务端内部替换实现类来完成。这条约束是有意的——协议一旦
> 分叉，客户端与服务端的兼容矩阵就会失控。

## 2. 新增语言方向（S1）

### 2.1 服务端

```python
# server/app/protocol.py
LANG_NAMES: dict[str, str] = {"en": "英语", "zh": "中文", "ja": "日语"}
SUPPORTED_LANGS: tuple[str, ...] = ("zh", "en", "ja")
```

加一门语言 = 在这两个结构中登记 + 确认 whisper 支持该语言的识别（`medium` 支持 99 种）。
校验发生在 `protocol.parse_config()`，非法取值回 `error(1001)`，不会污染下游。

### 2.2 提示词

`translate.build_prompt()` 用 `LANG_NAMES` 把语言码填进 `SYSTEM_PROMPT`，
所以只要登记了 `LANG_NAMES`，提示词自动支持新语言对，无需改模板。

### 2.3 客户端

`WsClient` 的 `srcLang` / `tgtLang` 构造参数默认 `en`→`zh`；UI 目前的"语言：英语 → 中文"
是**写死的展示文案**（`ControlScreen.kt`）。要做语言选择器，需要：

1. `UiState` 加 `srcLang` / `tgtLang` 字段；
2. `ControlScreen` 用下拉框选择，写回 `AppState`；
3. `WsClient.connect()` 里从 `AppState` 读取（与 E1 的 token 读取方式一致），
   在 `config` 消息中带上。

### 2.4 验证

```bash
cd server && ../.venv/bin/python -m pytest -q tests/test_protocol.py
.venv/bin/python scripts/mock_client.py --wav server/tests/fixtures/sample_en.wav \
  --src en --tgt ja --realtime     # 看服务端是否接受该方向
```

## 3. 替换翻译后端

### 3.1 接口契约

```python
class Translator(Protocol):
    async def translate(self, text: str, src_lang: str, tgt_lang: str) -> TranslateOutcome: ...
```

`TranslateOutcome` 是 `NamedTuple`：`text / degraded / error_code / elapsed_ms / usage / attempts`。

**两条硬性约定**（违反会导致上层降级逻辑失效）：

- **失败不抛异常**，返回 `degraded=True` 且 `text` 为原文（FM-02）。上层靠这个标记给字幕
  打 `degraded` 字段，客户端据此把译文标灰。
- `usage` 用 OpenAI 字段名（`prompt_tokens` / `completion_tokens`），否则 `CostMonitor`
  统计为 0。

### 3.2 新增一个后端（以 E2 的 Ollama 为模板）

`OllamaTranslator` 只覆写了三个钩子，这就是最小实现量：

```python
class MyTranslator(DeepSeekTranslator):
    backend_name = "my-backend"

    def _headers(self):     return {"X-Api-Key": self.settings.my_key}
    def _chat_url(self):    return f"{self.base_url}/v1/chat/completions"
    def _warm_url(self):    return f"{self.base_url}/health"
```

如果目标端点不是 OpenAI 兼容的，直接继承 `object` 实现 `translate()` 即可，
参考 `NullTranslator`（最短实现，12 行）。

### 3.3 注册与配置

```python
# server/app/translate.py :: build_translation_service()
if settings.translate_is_local:      translator = OllamaTranslator(settings)
elif settings.translate_configured:  translator = DeepSeekTranslator(settings)
else:                                translator = NullTranslator()
```

新增后端时：①`Settings` 加后端名到 `_check_backend` 的白名单；②`build_translation_service()`
加一个分支；③若不计费，在 `TranslationService.__init__` 里把单价置零（参考 `translate_is_local`）。

### 3.4 验证

```bash
# 单元测试（不联网）：替身 httpx 客户端注入 _client 即可
.venv/bin/python -m pytest -q tests/test_translate.py tests/test_translate_ollama.py

# 真实端点回环：起一个假 Ollama，走完整 HTTP 路径
.venv/bin/python -m pytest -q tests/test_ollama_local_http.py

# 人工确认：对真实本地端点跑三句
.venv/bin/python scripts/verify_ollama.py
```

## 4. 新增音频源（Android）

```kotlin
interface AudioSource {
    fun start(onFrame: (ShortArray) -> Unit)   // 每次回调 1600 采样点（100ms @16kHz）
    fun stop()
}
```

新增源要做三件事：

1. 实现 `AudioSource`，**保证输出 16kHz 单声道 PCM16**；重采样用现成的
   `LinearResampler`（`audio/LinearResampler.kt`），不要自己写。
2. 在 `CaptureMode` 枚举加一项（`AppState.kt`），并在 `CaptureService` 的
   `when (mode)` 分支里构造它。
3. 更新 `ControlScreen` 的模式按钮与 `strings.xml`。

**不要**在 `AudioSource` 里做断句或编码——帧化由 `FrameAccumulator` 负责，
断句在服务端 VAD 里做，客户端只负责"按时送 100ms"。

## 5. 鉴权与 TLS 部署（E1，已实现）

### 5.1 服务端开关

```ini
# server/.env
AUTH_TOKEN=<随机串>          # 非空即启用；留空 = 不鉴权（仅限可信局域网）
SSL_CERTFILE=certs/dev-cert.pem   # 可选：服务端直出 wss
SSL_KEYFILE=certs/dev-key.pem
```

```bash
python -c "import secrets;print(secrets.token_urlsafe(24))"   # 生成令牌
python scripts/gen_dev_cert.py --ip 192.168.1.10              # 生成自签证书（仅调试）
```

行为：令牌错误/缺失 → `error(1003)` + 关闭码 **4401**，且**在分配会话之前**拒绝，
不产生任何识别开销。令牌比较用 `hmac.compare_digest`（定长，防时序侧信道）。

### 5.2 客户端

Android 控制页的「访问令牌」与「wss」开关（`ControlScreen.kt`）写入 `UiState`，
`WsClient.connect()` 据此拼 `wss://…&token=…`。收到 4401 时**停止自动重连**并提示
检查令牌（否则会每 10 秒撞一次墙）。

### 5.3 三种公网接入方式

| 方式 | 服务端配置 | 客户端地址 | 说明 |
|---|---|---|---|
| 服务端直出 TLS | `SSL_CERTFILE` / `SSL_KEYFILE` | `wss://ip:8000/ws?token=…` | 最简；自签证书需在手机上装信任 |
| frp 隧道 | 只填 `AUTH_TOKEN`，服务端监听 127.0.0.1 | `wss://frp域名/ws?token=…` | 推荐：TLS 由 frps 终结 |
| nginx 反代 | 只填 `AUTH_TOKEN` | `wss://域名/ws?token=…` | 需要 `proxy_set_header Upgrade/Connection` |

nginx 关键片段：

```nginx
location /ws {
    proxy_pass http://127.0.0.1:8000;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_read_timeout 3600s;   # 长连接，别用默认 60s
}
```

frpc 关键片段（TLS 在 frps 侧配证书）：

```ini
[bilingual-subtitle]
type = tcp
local_ip = 127.0.0.1
local_port = 8000
remote_port = 8000
```

> **不要**把明文 `ws://` 直接暴露到公网。E1 的完整定义是"wss **且** 鉴权"，
> 只做其中一半等于把语音通道裸露在互联网上（03 文档 §2、07 报告 §6.4）。

### 5.4 验证

```bash
# 1) 服务端开启 AUTH_TOKEN + TLS 后启动
# 2) 命令行验证（Python 3.9+，websockets）
python - <<'PY'
import ssl
from websockets.sync.client import connect
ctx = ssl.create_default_context(); ctx.check_hostname = False; ctx.verify_mode = ssl.CERT_NONE
with connect("wss://127.0.0.1:8443/ws?token=<令牌>", ssl=ctx) as ws:
    print(ws.recv()[:80])          # → {"type":"hello",...}
PY
```

预期：不带 `token` 时收到 `{"type":"error","code":1003,...}`，随后连接以 4401 关闭
（M4 已实测，见 10 文档 §3.3）。

更省事的办法是用仓库自带的模拟客户端，它会打印鉴权提示并给出修复建议：

```bash
.venv/bin/python scripts/mock_client.py --host 127.0.0.1 --port 8000 --tls --token <令牌> --fast
# 不带令牌时输出： [失败] 鉴权被拒（4401）：令牌缺失或不匹配。
```

## 6. 在 Linux 上运行（E3，已实现）

```bash
# 1) 依赖：与 Windows 完全一致
python3 -m venv .venv
.venv/bin/python -m pip install -r server/requirements.txt

# 2) 配置
cp server/.env.example server/.env    # WHISPER_DEVICE=cuda 或 cpu

# 3) 启动 / 停止
./start_server.sh        # 等价于 start_server.bat：端口预检 → 打印手机端应填 IP
./stop_server.sh         # 只结束监听该端口的 Python 进程

# 4) 常驻：systemd
sudo cp deploy/bilingual-subtitle.service /etc/systemd/system/
sudoedit /etc/systemd/system/bilingual-subtitle.service   # 改 User / WorkingDirectory
sudo systemctl enable --now bilingual-subtitle
```

**CPU 主机**：`WHISPER_DEVICE=cpu` + `WHISPER_COMPUTE_TYPE=int8`。`medium` 在 8 核 CPU 上
单句约 1.5~3s，会超出 NFR-01 预算；要么换 `small`，要么接受延迟。

**CUDA 主机**：`requirements.txt` 已含 `nvidia-cublas-cu12` / `nvidia-cudnn-cu12`，
无需系统级安装 CUDA；驱动版本需 ≥ 525。`nvidia-smi` 能看到卡即可。

**已知坑（2026-11 实测）**：`faster-whisper 1.2.1` 调用 `av.open(..., metadata_errors="ignore")`，
而 **PyAV ≥14 移除了该参数**，装了新版 PyAV 会在 `decode_audio` 处报
`TypeError: open() got an unexpected keyword argument 'metadata_errors'`。
本仓库验证通过的组合是 **PyAV 13.1.0**；若 `pip install -U av` 后测试大面积报错，
`pip install "av==13.1.0"` 即可。

## 8. 收敛建议

如果只改一处就能获得最大收益，优先顺序是：

1. **翻译后端**（收益最大、改动最小）：`Translator` 只有一个方法，测试脚手架齐备；
2. **语言对**：登记两处即可，提示词与校验自动生效；
3. **音频源**：收益取决于平台，Android 侧改动集中在 3 个文件；
4. **协议**：除非必要不要动。字段只增不改，旧客户端必须仍能连上新服务端——
   这是 03 文档 §12 的兼容承诺，也是 M1~M3 真机验收的前提。
