## 2. E2：本地模型翻译（Ollama）

### 2.1 为什么先做 E2

01 文档把 E2 排在优先级第 2，理由是隐私：基础版只把**音频**留在内网，发往 DeepSeek 的
仍是**识别后的文本**。E2 把翻译换成本地模型后，音频与文本都不出内网，才真正满足
"企业保密会议"的完整愿景（NFR-11）。它的改动面也最小——03 文档预判"一个实现类 + 配置项"，
实际就是如此。

### 2.2 改动

| 文件 | 改动 |
|---|---|
| `server/app/settings.py` | 新增 `TRANSLATE_BACKEND`（`deepseek`/`ollama`，带白名单校验）、`OLLAMA_BASE_URL`、`OLLAMA_MODEL`、`OLLAMA_TIMEOUT_S`；新增 `translate_is_local` / `translate_model_name` 属性；`translate_configured` 对本地后端恒为真（本地不需要密钥） |
| `server/app/translate.py` | `DeepSeekTranslator` 抽出三个可覆写钩子 `_headers()` / `_chat_url()` / `_warm_url()`；新增 `OllamaTranslator`（无鉴权头、`/v1/chat/completions`、`/api/tags` 自检）；`build_translation_service()` 增加 ollama 分支；`TranslationService` 对本地后端把单价置 0（token 仍计数） |
| `server/app/main.py` | `/health` 增 `translate_backend` / `translate_model` / `auth_required` / `tls`；启动日志打印后端全名 |
| `server/run_server.py` | 启动横幅区分"本地 Ollama / 云端"，并打印鉴权与传输状态 |
| `scripts/verify_ollama.py` | **新增**：对真实 Ollama 做"可达性 → 模型是否已 pull → 三句真实翻译 → 纯净度"自检 |
| `server/tests/test_translate_ollama.py` | **新增 10 项**：配置校验、端点/请求头形态、失败降级、自检告警、零计费 |
| `server/tests/test_ollama_local_http.py` | **新增 2 项**：起一个假 Ollama（真实 socket + HTTP），验证客户端完整链路 |

### 2.3 关键设计决策

- **不新写一个抽象，而是复用 `DeepSeekTranslator` 的骨架**：Ollama 提供 OpenAI 兼容端点，
  两者的差异只有 base_url、模型名、鉴权头、健康检查路径。抽三个钩子比复制 100 行更省事，
  也让"再加一个 OpenAI 兼容后端"变成 3 行覆写（09 文档 §3.2）。
- **本地后端不做密钥校验**，但**仍然记录 token 用量**：`/status` 里能看到 `tokens_in/out`
  变化，`cost_yuan` 恒为 0。这样"成本监控"与"用量观测"两个职责解耦——本地方案也有
  推理量可看。
- **`warm_up()` 只查 `/api/tags`，不做一次空推理**：避免启动时把模型权重拉进显存
  （CPU 机器上这会多花十几秒且占内存）。模型缺失时打 warning 并直接给出
  `ollama pull <model>` 命令。
- **超时预算独立**（`OLLAMA_TIMEOUT_S=30`）：本地模型首次调用要加载权重，沿用云端 10s
  会把第一次字幕打成降级。

### 2.4 验证证据

本机（Ubuntu，无 GPU、未安装 Ollama）能验证到"客户端实现正确"这一层：

```
$ .venv-linux/bin/python -m pytest --tb=no tests/test_ollama_local_http.py
2 passed in 1.29s
```

该测试起了真实的 `ThreadingHTTPServer` 充当 Ollama，断言：请求打到
`/api/tags` 与 `/v1/chat/completions`、**所有请求的 `Authorization` 均为空**、
`usage` 进入 `CostMonitor` 且 `cost_yuan == 0.0`。

**未验证项**：真实 `qwen2.5:7b-instruct` 的译文质量与延迟。原因：本机未安装 Ollama，
模型权重约 4.7GB。部署方按下面命令可自测（脚本会给出明确失败原因）：

```bash
ollama serve & ollama pull qwen2.5:7b-instruct
TRANSLATE_BACKEND=ollama .venv/bin/python scripts/verify_ollama.py
```

预期：CPU 上单句数秒级，明显慢于云端；这也意味着**本地后端不适合把 NFR-01 的
800ms/1500ms 预算当作验收线**——那组预算针对云端接口，本地方案的收益是隐私而非延迟。
这一点在 07 报告 §7.3 的扩展路线里已写为"换本地模型后延迟会变差"，本次实测未推翻该判断。

## 3. E1：token 鉴权与 wss

### 3.1 改动

| 文件 | 改动 |
|---|---|
| `server/app/settings.py` | 新增 `AUTH_TOKEN`、`SSL_CERTFILE`、`SSL_KEYFILE`；`auth_required` / `tls_enabled` / `scheme` 属性；启动时给出"已启用鉴权但未配 TLS"的提示 |
| `server/app/protocol.py` | 新增错误码 `1003 鉴权失败`（recoverable=False）与关闭码 `WS_CLOSE_UNAUTHORIZED = 4401` |
| `server/app/connection.py` | 新增 `extract_token()`（query 或 `Authorization: Bearer`）与 `token_ok()`（`hmac.compare_digest`）；握手时**在分配会话之前**校验，失败回 1003 并以 4401 关闭 |
| `server/run_server.py` | 配置证书时把 `ssl_certfile/ssl_keyfile` 传给 uvicorn，服务端直出 wss；提示文案按平台区分（Linux 指向 `stop_server.sh`） |
| `scripts/gen_dev_cert.py` | **新增**：openssl 生成带 SAN 的自签证书，私钥 chmod 600，打印可直接粘贴的 `.env` 两行 |
| Android `WsClient.kt` | URL 按 `UiState.useTls` 选 `ws/wss`，按 `UiState.authToken` 追加 `&token=`；收到 **4401 停止自动重连**并提示检查令牌 |
| Android `AppState.kt` / `ControlScreen.kt` | `UiState` 新增 `authToken` / `useTls` 与对应 setter；服务器卡片新增「访问令牌」输入框与「wss」开关（采集中禁用） |
| `server/tests/test_auth.py` | **新增 9 项**：令牌解析/比较、缺失/错误令牌被拒（1003+4401）、query 与 header 两种携带方式、未开启鉴权时放行、`/health` 不泄露令牌 |

### 3.2 关键设计决策

- **先 accept 再判鉴权**：WebSocket 协议要求先完成握手才能发消息；因此顺序是
  `accept()` → 校验 → 失败则 `send(error 1003)` → `close(4401)`。这与"协议版本不支持"
  的处理一致（03 文档 §2）。
- **拒绝发生在会话分配之前**：`registry.get_or_create()` 在鉴权之后才调用，
  未授权连接不会创建 Session、不会占用会话表、不会触发任何 ASR。
- **定长比较**：`hmac.compare_digest` 而不是 `==`，避免逐字节比较的时序侧信道。
  令牌不写日志，只记录客户端 IP。
- **4401 让客户端停下来**：如果只发 error 就断开，客户端按 1/2/4/8s 退避重连会一直撞墙。
  4401 是应用私有码，客户端据此判定"重连无用"，直接进入 FAILED 并提示。
- **TLS 不强制**：局域网内 `ws://` 仍可用（M1~M3 的验收路径不变）；只有暴露公网时才
  要求 wss。服务端不因为没配证书就拒绝启动——否则会破坏既有的真机流程。

### 3.3 验证证据（真实 TLS + 真实 WebSocket）

本机用 `scripts/gen_dev_cert.py` 生成自签证书，起服务端（stub ASR/翻译，`load_model=False`）
监听 `127.0.0.1:8500` 并启用 TLS + `AUTH_TOKEN=tok-abc`，然后用 `websockets` 客户端连：

```
--- 1) 带正确 token ---
收到： {"type":"hello","protocol_version":1,"server_version":"0.2.0",
      "server_time":1793606638890,"limits":{"max_sentence_ms":8000,...}}
--- 2) 不带 token ---
收到： {"type":"error","code":1003,"message":"令牌无效或缺失","recoverable":false}
已断开： ConnectionClosedError 4401 received 4401 (private use); then sent 4401 (private use)
```

再往上一层，用仓库自带的模拟客户端把**完整链路**跑通（真实 VAD + 真实 WebSocket 帧，
ASR/翻译用替身以便离线复现）：

```
$ .venv-linux/bin/python scripts/mock_client.py --host 127.0.0.1 --port 8500 --tls --token tok-abc --fast
服务端   : wss://127.0.0.1:8500/ws?protocol_version=1&token=tok-abc
传输     : wss（不校验证书（自签调试））
鉴权     : 已携带令牌
[字幕 #1] stub → 译文:stub        ← 5 句全部返回
...
```

```
$ .venv-linux/bin/python scripts/mock_client.py --host 127.0.0.1 --port 8500 --tls
[失败] 鉴权被拒（4401）：令牌缺失或不匹配。
       → 用 --token <AUTH_TOKEN> 重试；服务端未开启鉴权时请不要带 --token。
```

即：**wss 握手成功、令牌生效、拒绝路径的关闭码正确**，且整条管道（帧→VAD→ASR→翻译→字幕）
在 TLS + 鉴权下仍能出字幕。单测侧：

```

所以写进了文档与本节。若后续升级 faster-whisper，需要重新核对与 PyAV 的兼容区间。

## 6. E4 调研：iOS 与鸿蒙（结论：不实施原型）

### 6.1 iOS

- **麦克风模式可行**：服务端与协议完全复用，只需用 `URLSessionWebSocketTask` 重写
  `WsClient`，音频用 `AVAudioEngine` 取 16kHz PCM16。工作量约 1 人周。
- **媒体声音模式不可行（系统限制）**：iOS 没有等价的 `AudioPlaybackCapture`。唯一途径是
  **ReplayKit Broadcast Upload Extension**，它拿到的是整个屏幕录制的样本缓冲，
  需要自己解码、且受"仅前台/用户显式开始录制"限制，体验与 Android 的跨应用悬浮字幕差距大。
- **悬浮窗**：iOS 不允许跨应用浮层。可行替代是画中画（PiP）承载字幕，但 PiP 只接受视频，
  需要把字幕渲染成视频帧——复杂度高、耗电。
- **结论**：做"麦克风模式 + 应用内字幕"原型是现实的；"媒体字幕 + 跨应用悬浮窗"在 iOS 上
  无法达到 Android 的形态，应在需求层面就降级说明。

### 6.2 鸿蒙

- **HarmonyOS 4.x 及以下**：兼容 Android APK，可直接安装 M2 的产物（README 已注明）。
- **HarmonyOS NEXT（5/6）**：纯 ArkTS/ArkUI，AOSP 兼容层被移除，只能经 Android 容器运行
  且媒体声音与跨应用悬浮窗大概率不可用（README 已注明）。
- 原生重写需要：`@ohos.multimedia.audio` 采集 + `@ohos.net.webSocket` + 悬浮窗
  （`window.createWindow` + `SYSTEM_FLOAT` 权限，需申请）。协议层可 100% 复用。
- **结论**：NEXT 原生客户端属"独立工程"级别（估 2~3 人周），不适合作为课程项目的收尾工作；
  建议在报告中作为"平台能力差异"的论据，而不是承诺交付。

### 6.3 建议路线（若后续继续）

1. iOS 麦克风模式原型（协议不变，只换传输与采集）；
2. 鸿蒙 NEXT 采集层 PoC，验证 `SYSTEM_FLOAT` 悬浮窗是否真能跨应用；
3. 两者都需要"服务端多客户端调度"（当前 `MAX_QUEUE=10` 是按单客户端调的）。

python3 -m venv .venv && .venv/bin/python -m pip install -r server/requirements.txt

# 1) 全量测试（应为 75 passed）

# 2) E2 本地翻译

TRANSLATE_BACKEND=ollama ./start_server.sh        # 启动后 /health 应显示 translate_backend=ollama

# 3) E1 鉴权 + wss
.venv/bin/python scripts/gen_dev_cert.py --ip <本机局域网IP>
# 在 server/.env 写入 AUTH_TOKEN / SSL_CERTFILE / SSL_KEYFILE 后启动
curl --noproxy '*' -k https://127.0.0.1:8000/health

# 4) E3 常驻
sudo cp deploy/bilingual-subtitle.service /etc/systemd/system/
sudo systemctl enable --now bilingual-subtitle && journalctl -u bilingual-subtitle -f
```
