**实现中发现并修正的问题**（均已落库，见 05 文档 §3）

1. **VAD 模型并非跨调用有状态**：`faster_whisper.vad.SileroVADModel.__call__` 每次调用把
   LSTM 状态 `h`/`c` 重置为零，直接分块调用会丢失时间上下文。服务端改为**自行持有**
   ONNX 会话与 `h`/`c`/64 采样点前置上下文（03 文档 §9.3 已相应修正）。
2. **冷启动污染延迟统计**：首次 ASR 推理（CUDA kernel 初始化）1700ms、首次翻译请求
   （TLS 建连）达 4871ms，会把首句字幕的延迟严重拉高。已在模型加载后**预热一次推理**、
   在服务启动时**预热翻译端点连接**（仅一次 GET，不消耗 token）。
3. **端到端延迟口径**：原按「首帧时间 + 标称音频位置」估算，会被客户端发送漂移污染
   （实测偏差近 2 倍）。改为**按每帧实际到达时刻**查表计算，服务端统计与客户端实测一致。
4. **FastAPI 参数注解**：`@app.websocket` 处理函数的 `websocket` 参数若不加类型注解，
   会被当作查询参数校验导致连接被拒（1008）。已注解为 `WebSocket`。
5. **会话过期导致逐句统计丢失**：延迟与错误计数原先挂在单个 Session 上，断线 30s 后会话被
   回收，`/status` 的句数与 P95 归零（实测出现过「翻译调用 21 次但 sentences=0」）。
   已改为 `SessionRegistry` 共享一个 `LatencyStats`，**跨会话累计**；丢帧/非法帧计数也
   在会话内增量累加，避免缓冲区重置后重复或丢失。新增 2 项单元测试覆盖回收后仍保留。
6. **重连后延迟虚高**：重连/切换配置会重置断句器时间轴，但接收帧的到达时刻表未清空，
   句末会查到旧帧，产生几十秒甚至 **202s** 的假延迟（实测 103 句数据 P95 被抬到 8.5s）。
   → 新增 `Session.reset_audio_clock()`，在 `apply_config` / `reset` / 重连时与
   `segmenter.reset()` 同步清空；新增 2 项时钟测试，并增加 `/latency` 逐句明细接口。

**媒体声音问题的定位与改进（2026-10-19）**

现象是"媒体模式无字幕"，可能原因有两类：①捕获到的音频为静音（目标应用禁止捕获 / DRM /
OEM 对纯音频投影的限制）；②捕获正常但管道未触发。为区分二者，已加入：

1. **实时电平显示**：媒体模式下在「采集模式」卡与「状态」卡显示「媒体音量：xx%」，
   未开始时显示「未开始」；直接反映捕获到的 RMS。
2. **静音看门狗**：连续 8 秒无有效电平即显示可操作提示（"确认正在播放；应用可能禁止捕获，
   可改用麦克风模式"），并在有声音后自动清除。
3. **1×1 VirtualDisplay 保活**：部分 OEM（含华为部分机型）在纯音频捕获时不保持投影会话，
   导致 AudioRecord 持续读到静音；镜像到未读取的 1×1 Surface 可规避。
4. 日志保留条数由 8 条增至 20 条，便于无 adb 环境下截图定位。

**复测判据**：播放视频时若「媒体音量」> 0% 但仍无字幕 → 问题在服务端/断句；若为 0% 并出现
8 秒提示 → 捕获被目标应用或系统禁止，换应用（第三方播放器/浏览器）或改用麦克风模式。

**复测记录（2026-10-19）**：

1. 华为「图库」播放本地视频：媒体音量持续 0%，8 秒提示正常出现；
2. 另装第三方播放器、酷狗音乐：同样为 0%。

→ 判定为**华为系统级音频捕获限制**（非链路故障，也非单个目标应用的策略）。该机无法完成
FR-02 媒体声音演示。正式演示改用已约定的 Android 真机；本机可用**麦克风模式 + 外放**
（播放视频时用麦克风拾取扬声器声音）作为兜底，但音质与体验不等同于内录。

**真机验证通过（2026-10-19，Redmi Pad SE）**

用户改用 **Redmi Pad SE（Android 15 / HyperOS 2.0.208.0.VMUCNXM）** 复测，六项全部通过：
麦克风模式、**媒体声音模式（可正常出字幕）**、悬浮窗（显示/拖动/透明度/关闭）、
前台服务后台保活、断线重连、停止与冲刷。华为机的媒体内录限制作为 ROM 级兼容性记录保留。

**交互问题修复（v0.1.4）**

1. **采集中切换模式**：此前点击另一模式只改变界面选中态，实际仍在旧模式。现改为真正切换：
   - 切到麦克风：前台服务重启采集（无需新授权）；
   - 切到媒体声音：先请求新的 MediaProjection 授权，再重启采集；
   - 切换期间输出日志；重启前先注销并停止旧投影，避免 `onStop` 回调误停新会话。
2. **悬浮窗关闭状态不同步**：此前点 × 后 App 内开关仍显示开启，需要关一次再开。现开关
   直接绑定 `AppState.overlayEnabled`，关闭后立即同步为关，可直接重新打开。

#### M3 操作单（可直接照做）

**前置**：客户端 v0.1.4；平板与服务端在同一网段（热点/局域网）或 ZeroTier 互通；

| 0 准备 | 记录 `nvidia-smi` 空闲显存 → `stop_server.bat` → `start_server.bat` → 再记录一次显存；`monitor_m3.bat` 开始采样；平板浏览器打开 `/health`。**测试期间关闭占用 GPU 的桌面应用**（游戏/视频/浏览器硬件加速），减少 ASR 抖动 | 返回 JSON；模型显存增量可算；CSV 开始写入 |
| 1 媒体模式 ≥10min | 选媒体声音 → 授权 → 播放长视频（**不要同时开系统录屏**，会抢占投影） | 字幕持续出现；媒体音量 >0%；无崩溃 |

agent 据此计算 NFR-01 的 P95、核对 NFR-04/NFR-05，并修复发现的问题。

**M3 首轮数据（2026-10-19，128 句，3 个会话）**

| 指标 | 结果 |
|---|---|
| 端到端 | 平均 2960ms，P50 2541ms，**P95 5211ms**，最大 9640ms |
| ASR | P95 3680ms，最大 8478ms（长句 8–15s 时中位实时率 10.9x，尖峰时低至 1.2x） |
| 翻译 | P95 1597ms，最大 3439ms |
| 队列等待 | P95 369ms，最大 2572ms（少数短句集中入队） |
| 固定开销（VAD 静音等待等） | 中位 524ms，符合 500ms 设计 |
| 错误/降级/丢帧 | 均为 0 |

**结论**：**未达到 NFR-01 的 P95 ≤3s**。主因是 ①长句（媒体连续语音触发 15s 上限）导致 ASR 1–3s；
②少量 ASR 尖峰（最高 8.5s，疑似 GPU 争用/抖动）；③翻译 P95 1.6s。固定开销正常。
下一步：关闭 GPU 占用后复测；若仍超预算，再评估将 `VAD_MAX_SENTENCE_MS` 从 15s 调至 8s
（配置项，但属 FR-05 默认值变更，需记录）或改用更快的 ASR 精度/模型。

**显存与内存（2026-10-19 实测）**：开机空闲 **904 MB** → 服务端加载模型后 **2566 MB**
（模型约 **1.66 GB**，整卡 2.57 GB < 6 GB）；服务端进程 RSS 约 **615 MB**。NFR-05 两条均满足。

**8s 上限对照实验（主机，同一段连续语音）**

| 切分长度 | ASR 平均 | p50 | 每秒音频耗时 |
|---|---|---|---|
| 15s | 1150ms | 1295ms | 77ms/s |
| 8s | 733ms | 831ms | 92ms/s |
| 4s | 594ms | 593ms | 149ms/s |

`int8_float16` 无额外收益（15s 段 1550ms，8s 段 774ms），保持 `float16`。
已在本地 `server/.env` 将 `VAD_MAX_SENTENCE_MS` 设为 **8000** 做复测实验；仓库默认仍为 15000，
若实验确认有效并采用，需同步修改 FR-05 并记录“8s 强制切句”的取舍（连续语音可能被更早截断）。

**8s 复测（2026-10-19，28 句）**

| 指标 | 结果 |
|---|---|
| ASR | P95 **1376ms**（15s 上限时为 3680ms） |
| 端到端 | 平均 2749ms，P50 **2375ms**，P95 5958ms，最大 6521ms |
| 翻译 | 25/28 句 ≤2s；3 次异常约 **4.8s**（4827/4867/4868ms） |
| 排除 3 次翻译尖峰后 | 平均 2343ms，**P95 2898ms（≤3s）** |

结论：8s 上限明显改善了 ASR 与整体延迟，**P95 已只剩外部翻译 API 的偶发尖峰**。
另一项 20 次单独探测的翻译延迟为 559~1615ms（中位 826ms），未复现 4.8s，判定为外部抖动。
已增加 `translate_attempts` / `translate_retries` 诊断字段与 >2s 慢响应日志，并把 HTTP
keepalive 从默认 5s 提升到 60s（句子间隔 8~15s，避免频繁重建连接）。
